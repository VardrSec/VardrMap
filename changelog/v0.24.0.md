# v0.24.0 — 2026-08-12

## Execution is now authorized, not merely recorded

**Breaking for `pentest`, `red_team`, and `internal` engagements.**

`Authorization` has stored `window_start`, `window_end`, and `status` since
v0.22. Nothing read them. Grepping `jobs.py`, `scans.py`, `runner.py`, and
`schedules.py` for `Authorization` returned nothing — the platform recorded the
authority to test and then ignored it.

On a product whose premise is *authorized* security testing, that is a
default-allow. A scan could be dispatched against a client whose authorization
was expired, suspended, or revoked, and the only trace would be a record
asserting it should not have happened.

### The policy engine

`backend/policy.py` is a pure module — no SQLAlchemy, no FastAPI, no I/O.
Callers assemble a `PolicyInput`; it returns a `PolicyDecision` with `allowed`
and a stable reason code. `backend/enforcement.py` is the thin database-aware
adapter that gathers facts, audits denials, and raises HTTP 403.

Execution is denied when:

| Reason code | Condition |
|---|---|
| `stop_work_active` | The emergency brake is engaged |
| `engagement_not_active` | Engagement status is not `active` |
| `authorization_missing` | Non-bounty engagement with no authorization record |
| `authorization_not_active` | Authorization status is not `active` |
| `outside_testing_window` | Now is before `window_start` or after `window_end` |
| `capability_prohibited` | The tool is not in the authorization's permitted set |
| `target_excluded` | An explicit exclusion matches |
| `target_out_of_scope` | No in-scope rule matches |
| `scope_ambiguous` | The target cannot be resolved to a host, IP, or URL |

**Exclusions beat inclusions unconditionally** — not "most specific wins". An
operator who wrote an exclusion meant it, and a broad wildcard must never
silently re-admit a carved-out host. **Ambiguity denies.**

Scope matching handles apex domains, implicit subdomains, `*.` wildcards, IPs,
CIDRs, URLs, and API route prefixes. Targets are normalized first, so
`https://user:pass@API.Acme.com:8443/v1` and `api.acme.com` match the same rule
— and credentials in a URL are stripped before any comparison.

### Enforced at two points

Job **creation** and job **claim**. A single check at creation would make the
testing window advisory: a job queued while the window was open and claimed an
hour after it closed would still run. Same for stop-work engaged after queuing.
Both have dedicated tests.

### Stop-work switch

`POST /engagements/{id}/stop-work` engages the brake; `DELETE` releases it.
While engaged, every execution is denied regardless of scope, window, or
authorization.

Engaging is idempotent — during an incident an operator needs certainty the
brake is on, not an error about pulling it twice. Any member with write access
may engage a stop; **only the owner may release one**, because stopping is a
safety action and resuming is an authorization decision.

### Bug bounty is unaffected

`bug_bounty` engagements skip the authorization-record requirement — the
programme's published policy is the authority and there is no counterparty to
sign an SOW. Scope, exclusions, stop-work, and status still apply. Since
`engagement_type` defaults to `bug_bounty` and `engagement_status` to `active`,
**existing engagements continue to work unchanged**.

### Zero-target jobs are allowed

The first implementation denied jobs resolving to no targets. That broke 41
existing tests, and the tests were right: a job with zero targets executes
nothing, so refusing it prevents nothing. Engagement-level gates still apply, so
the brake still stops a zero-target job. Recorded in
[ADR 0001](../docs/adr/0001-central-policy-engine.md).

### Audit

Denials are written to `audit_logs` with `action="deny"`, the reason code, and a
human-readable detail. A refused execution attempt is the security-relevant
event. `audit_logs.program_id` gains an index for that query.

### Migration `0016_policy_engine`

Additive and reversible. Adds `programs.stop_work_at` / `stop_work_reason`,
`audit_logs.reason` / `detail`, the index, and a Postgres CHECK constraint on
`authorizations.status` — which previously documented six states in a comment
while the database accepted any string. Verified upgrade and downgrade against a
seeded database.
