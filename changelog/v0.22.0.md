# v0.22.0 — 2026-08-04

## Programs are now Engagements

The entity is renamed throughout the API, the frontend, and the codebase.
Bug bounty work becomes one `engagement_type` among several rather than the
shape the whole product is built around.

- `/programs/*` → `/engagements/*`. **The old paths still work** —
  `LegacyProgramPathMiddleware` rewrites them before routing, so VardrRunner
  (its own repo, its own deploy) and any `vmap_` key scripts keep working.
  `GET /engagements` returns both an `engagements` and a `programs` key
  carrying the same list, for the same reason.
- `class Program` → `Engagement`, `ProgramMember` → `EngagementMember`, and the
  matching frontend types, state keys, and actions.

**Not renamed, deliberately:**

- The `programs` table and its 14 `program_id` foreign keys. Renaming them means
  `ALTER TABLE` against a live database while `start.sh` is bringing uvicorn up
  on the old shape, for zero user-visible benefit. Scheduled separately in
  `docs/roadmap.md`.
- **`RadarProgram` and everything under `/radar`.** Those are real bug bounty
  programmes on HackerOne and Bugcrowd. They are not engagements, and calling
  them that would lose exactly the precision this rename is for.

## Engagements: clients and authorization records

The first step in widening VardrMap from a bug bounty workspace into a platform
for professional security testing. Bug bounty work becomes one engagement type
among several rather than the shape everything is built around.

Everything here is **additive**. No column was dropped, renamed, or made
required; no existing endpoint changed its response shape beyond gaining new
keys. A caller that sends none of the new fields creates exactly what it created
before — a bug bounty programme — and existing rows backfill to `bug_bounty`,
because that is what they genuinely are.

### Clients

An organisation engagements are performed for. Bounty work has none, which is
why the link is optional.

- `GET /clients`, `POST /clients`, `GET|PATCH|DELETE /clients/{id}`
- Scoped to the creating user. Another user's client returns `404`, never `403`,
  so existence is not confirmed.
- **Not** shared through program membership: a collaborator invited to one
  engagement should not see the other engagements a client record covers.
- **Deleting a client detaches its engagements rather than deleting them.** The
  testing record outlives the commercial relationship; losing a year of findings
  to a tidy-up would be an expensive surprise.

### Authorizations

The record of permission to test, and the window it covers — the artifact that
separates a professional engagement from bounty hunting. A named person
authorised named activity, between two dates.

- `GET|POST /programs/{id}/authorizations`
- `PATCH /programs/{id}/authorizations/{authorization_id}`
- `GET /programs/{id}/authorization/active` — the authorisation permitting work
  *right now*, or `null`. An authorisation qualifies when its status is `active`
  and the present moment falls inside its window; a missing window bound is open
  on that side, which is normal for a bounty programme and unusual for an
  engagement.
- Append-mostly by design. Supersede an authorisation by marking it `expired`
  and creating a new row, rather than editing it — the record's value is being
  able to say later what was permitted at the time.
- Access is scoped through the program; viewers cannot create or edit one.

`GET /programs/{id}/authorization/active` exists to be asked by the rest of the
toolchain before it runs anything. Enforcement is not wired up yet; this release
only establishes the record.

### Engagement context on programs

`POST /programs` and `PATCH /programs/{id}` accept, and the program object now
returns:

- `client_id` — validated as owned by the caller. Another user's id returns
  `404`, so the field cannot be used to probe for the existence of their records.
- `engagement_type` — `bug_bounty` (default), `pentest`, `red_team`, `internal`
- `engagement_status` — `active` (default), `planned`, `reporting`, `closed`
- `starts_at` / `ends_at` — the contracted testing window

Dates are ISO-8601 strings, matching how the API serialises them on the way out.
An unparseable date returns `422` rather than being written to the column.

### Migration

`0013clientsauthorizations` — creates `clients` and `authorizations`, adds five
nullable/defaulted columns to `programs`. Additive in both directions with a
tested downgrade.

### Tests

431 backend tests, up from 391, plus 70 frontend tests. New coverage for client CRUD and isolation,
authorization windows and revocation, cross-program authorization access, and
the client-ownership guard on both program create and update.
