# v0.32.0 — 2026-08-17

## VardrGate authorization testing, end to end

`vardrgate_api_test` is queueable. VardrRunner has had a complete handler for it
for some time; what was missing was all on this side. v0.31.0 landed the storage,
this release closes the remaining four steps — **with no VardrRunner change
required**.

An engagement can now store an authorization test case, queue a job against it,
have the runner execute it, and get the findings back as triageable results with
the request/response record attached.

### The spec is inlined at hand-off

A vardrgate job stores only `config = {"test_case_id": ...}`. `GET /jobs/pending`
expands that into `config.test_case` when handing the job to a runner:

```json
{
  "tool_type": "vardrgate_api_test",
  "config": {
    "test_case_id": "<uuid>",
    "test_case": { "id": "bola-check", "identities": [ ... ], "request": { ... } }
  }
}
```

This is the piece that avoids a VardrRunner release: `VardrGateConfig.from_dict`
receives exactly the object it already expects, while `ScanJob.config` stays flat
so config validation is unchanged.

The expansion lives in that response only. It is never written back, so revising
a case changes what the next hand-off carries rather than leaving jobs holding
stale copies. A job whose case has since been deleted is auto-failed with
`"authorization test case ... no longer exists"` — it can never succeed, and
leaving it pending would hang the queue the way a dangling dependency does.

### Results land where results already land

`POST /jobs/{id}/upload` receives one VardrGate `engine.Result`:

| Result field | Becomes |
|---|---|
| `findings[]` | `scan_items` with `source="vardrgate"`, `status="new"` |
| `findings[].category` | `scan_items.type` (`potential_bola`, `cross_tenant_access`, …) |
| `findings[].severity` | `scan_items.severity` — same `info…critical` set as everywhere else |
| `test_case_id` | `scan_items.template_id` — the role a nuclei template id plays |
| the case's `request.url` | `scan_items.asset` / `matched_at` |
| `executions[]` | `evidence`, `kind="tool_result"`, content-hashed, `confidential` |

Reusing `scan_items` rather than inventing a parallel store means VardrGate
findings arrive in the Scanning section with the triage and promote-to-finding
flow already attached.

An unrecognised severity falls back to `info`. Upstream ranks unknown values
below info deliberately, and guessing upward would let an added level read as
critical.

**Everything is redacted on write.** VardrGate excludes credential values and
response bodies from its own JSON (`json:"-"`), so a well-behaved runner never
sends them — but a control that depends on the sender behaving is not a control.

### Queue-time validation

`config.test_case_id` is required and must name a case in the same engagement.
Both are checked when the job is queued rather than when it is claimed: a job
referencing a missing or borrowed case can never run, and refusing it up front
beats letting it sit pending until a runner picks it up and fails it. Scoping by
engagement also stops the field being used to pull another engagement's case.

### API Assessment pipeline

A third named chain: **httpx → vardrgate_api_test**. httpx confirms the API is
reachable and fingerprints it; vardrgate then replays the stored case as each
identity.

Selecting it — or the standalone `vardrgate` tool — shows a picker of the
engagement's stored cases, and **Queue** stays disabled until one is chosen,
since a vardrgate job without a case is a guaranteed `400`. Excluding the
vardrgate stage drops the requirement, so `httpx` alone still queues.

### Tests

720 backend (up from 700) and 75 frontend (up from 70).

Backend coverage: queueing against a stored case, the missing/unknown/borrowed
case paths, spec inlining, that the inlined spec is **not** persisted back onto
the job, that editing a case changes what the runner receives, auto-fail on a
deleted case, result upload creating scan items and evidence, redaction of a
credential that slips through anyway, unknown-severity fallback, and upload
rejection on a non-vardrgate job.

Frontend coverage: Queue disabled until a case is chosen, the reference riding on
the vardrgate stage rather than the httpx one, excluding the stage dropping the
requirement, and the empty-state message when no cases are stored.

Beyond the suites, the whole lifecycle — store → queue → poll → upload → triage —
was exercised against a real PostgreSQL instance over HTTP, which the SQLite
suite cannot cover: nested spec round-tripping through the JSON column, the
inlined spec genuinely not persisting, redaction landing in the stored body, and
the FK cascade firing on engagement delete.

### Known limitation

The result mapping was built by reading VardrGate's `engine.Result` and
`model.Finding` structs, not by running the tool. It should be confirmed against
one real invocation — `severity` most of all, since an unrecognised value
deliberately falls back to `info`.
