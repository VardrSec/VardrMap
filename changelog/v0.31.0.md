# v0.31.0 — 2026-08-16

## Authorization test cases — step 1 of the VardrGate integration

VardrRunner has a complete `vardrgate_api_test` handler. VardrMap could not queue
one, for two reasons: `VardrGateConfig` requires a structured `test_case` object
and `ScanJob.config` only carries flat scalars, and there was nowhere for the
runner to return results to.

This release lands the storage half. The tool is still **not** queueable — see
the roadmap note below.

### `authorization_test_cases`

A VardrGate authorization test case describes one request replayed as several
identities, with the access decision expected of each. That is the input to a
BOLA / BFLA / cross-tenant / privilege-escalation check.

- `GET|POST /engagements/{id}/test-cases`
- `GET|PATCH|DELETE /engagements/{id}/test-cases/{test_case_id}`

Cases are **referenced, not copied**. A job will carry
`config = {"test_case_id": "<uuid>"}` — a flat scalar, so job config validation
is unchanged — and the spec is inlined when the job is handed to a runner. One
case can back many runs, and revising a case will not require re-queueing.

`spec` stores VardrGate's own `AuthorizationTestCase` JSON verbatim rather than
being shredded into columns. VardrGate owns that schema and is free to extend it
without a migration here.

### Credentials are references, never values

**A credential carrying a non-empty literal `value` is rejected with `400`.**
Identities must reference their secret with `value_env` or `value_keychain`,
which VardrRunner resolves on the operator's machine.

This matters because VardrGate's own example test cases ship literal tokens —
convenient for a local run, but stored here that value would sit in the database
and travel in every API response for the case. It is the one place an operator
could paste a live bearer token into VardrMap, and the platform's standing rule
is that raw secrets are never stored.

An empty `value` is still allowed: `{"type": "static_header", "header": "",
"value": ""}` is the legitimate anonymous caller in a BOLA case.

### Validation

Beyond the credential rule, the spec is checked for the things VardrGate's own
`validate()` would reject at run time — `id`, at least one uniquely-identified
identity, `request.method`, `request.url`, a known `credential.type`, and that
every `expected_access.identity_id` matches a declared identity. Catching those
at write time beats failing on the operator's machine after a job is claimed.

### Migration

`0021authztestcases` — one new table, purely additive, no existing table touched.
Single head.

### Still to come

Steps 2–5 of the integration are listed in `docs/implementation-roadmap.md`:
inline the spec in `GET /jobs/pending`, add `POST /jobs/{id}/upload` mapping
findings to `ScanItem` and executions to `Evidence`, then add the tool to
`_VALID_TOOLS` and ship the API Assessment pipeline.

### Tests

700 backend tests, up from 680. Twenty cover this table, the load-bearing ones
being that a literal credential is refused on both create and update, that an
empty anonymous credential is not, and that a stored case never returns a secret.
