# v0.25.0 — 2026-08-12

## Organizations — tenancy is no longer anchored to a person

Before this, the tenancy anchor was a GitHub user id, denormalized onto
`clients`, `scan_jobs`, `scheduled_scans`, `authorizations` and `services`. Two
different access models ran side by side:

- Engagement-scoped resources used `get_engagement_or_404` — owner **or** member.
- Job, schedule and client endpoints filtered on
  `owner_github_id == current_user` directly — owner only.

The consequences were concrete. A teammate invited to an engagement could read
its findings but **could not see or operate its jobs**. The runner authenticates
as a user, so a team could not share runner infrastructure. And two consultants
at the same firm could not share a client record.

### What changed

`organizations` and `organization_members` are new. Roles are ordered:
`owner > admin > member > viewer`.

`deps.engagement_access()` resolves an effective role from **three** grants,
highest wins:

1. Direct ownership — the legacy anchor, still authoritative
2. Organization membership — the new tenancy path
3. Per-engagement invitation — how collaboration worked before

All three coexist deliberately. Dropping (1) or (3) in the same change that
introduces (2) would revoke access for every existing user the moment the
migration landed.

Every `owner_github_id == current_user` filter in `routers/jobs.py` — eleven of
them — now resolves through `accessible_engagement_ids()`. Job and schedule
access follows the engagement, not the row's creator.

### Personal organizations

Every user gets one, created lazily on first engagement creation. Single-operator
use is unchanged: the organization is invisible until somebody is invited into
it. `personal_for_github_id` marks it, which is also what makes the backfill
identifiable and reversible.

### Migration `0017_organizations`

Additive and backfilled, never destructive. Creates the two tables, adds
nullable `org_id` to `clients` and `programs`, then backfills one personal
organization per owner and points their rows at it.

`owner_github_id` is left in place on every table. Removing it is a later,
separate change once no code path reads it.

Verified against a seeded database: two users produced two personal
organizations with `owner` membership, every engagement and client got an
`org_id`, and `downgrade()` removed both tables with all engagement and client
rows intact.

### Tests

Sixteen new, asserting **both** directions. A teammate gains access; a stranger
gains nothing. The second matters more — widening an access check is exactly the
change that accidentally widens it too far:

- an org member can now list and claim the engagement's jobs, and sees them in
  `/jobs/pending` (the shared runner fleet)
- a stranger still gets `404` on read, create, list, and claim — never `403`,
  which would confirm the engagement exists
- an org `viewer` still gets `403` on write
- membership in *some* organization grants nothing in another

Backend suite: 552 → 568.
