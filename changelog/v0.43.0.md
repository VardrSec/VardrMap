# v0.43.0 — recon URLs stay intact

**Date:** 2026-10-10

**Bug fix. No migration.** New recon and nuclei imports store URLs exactly as the tool reported them.
Rows already stored are **not** touched; see [`docs/recon-url-recovery-plan.md`](../docs/recon-url-recovery-plan.md).

## What was wrong

Every importer ran URLs through `strip_html` (nh3), a sanitiser for prose. It does not return what it
is given: it HTML-encodes `&`, `<` and `>` and deletes anything tag-shaped. A URL `?q=1&page=2` was
stored as `?q=1&amp;page=2`.

That matters because recon URLs are **read back as scan targets**. A runner scanning that row fetched a
URL whose second parameter was literally named `amp;page`, so dalfox (which lives on multi-parameter
URLs) tested the wrong parameters, and anything keyed on the string — dedup, the asset graph, job
targets — was keyed on a value that was never the URL. Found while checking the stored row against a
real dalfox report; it affects every importer and predates dalfox.

## What changed

- `url`, `host` and `path` for `httpx`, `ffuf`, `katana` and `gau`, and `asset`/`matched_at` for
  `nuclei`, go through a lossless `_url_field`: control characters removed, 8192-character cap, nothing
  else touched.
- **`<` and `>` are percent-encoded** (`%3C`, `%3E`) rather than deleted. A URL can still never be stored
  as markup (the existing test for that still passes) but no part of it is lost, and the target means the
  same thing, since a literal `<` is not valid in a URL and every HTTP client sends it encoded anyway.
- Titles, descriptions and other descriptive text **still go through `strip_html`**.
- An original `a&b` and an original `a&amp;b` are now **distinct rows**. The old importer stored both as
  `a&amp;b`.

## What was deliberately not done

**Existing rows are not rewritten, and no import repairs them.** Decoding them blindly would be a guess:
measured against the real sanitiser, five different originals (`a&b`, `a&amp;b`, `a&#38;b`, `a&#x26;b`,
`a&ampb`) all became the same stored `a&amp;b`, and a bare `<` truncates everything after it, so a blind
decode would silently change literal-entity URLs (common in archive data) and cannot recover deleted
content at all.

At the boundary, dedup is on the exact string, so re-importing a URL whose legacy row is encoded adds the
correct row **beside** the old one. That is pinned by a test, because the alternative, skipping the
import, would silently drop the correct URL. httpx is the exception: it matches by host and enriches in
place, so its rows repair themselves on the next probe.

## Recovery

[`docs/recon-url-recovery-plan.md`](../docs/recon-url-recovery-plan.md) is a proposal for review: the
options, the safeguards any repair needs (dry-run default, backup first, and a checkable invariant that
the old sanitiser applied to the proposed original reproduces exactly what was stored), and open
questions. Nothing in it has been executed.

`backend/audit_recon_urls.py` is the read-only first step. It reports how many rows are affected, how
many are **corroborated** by a correct row that explains them, how many are **collisions**, and how many
are **unpaired** (no evidence at all). It issues only SELECTs inside the database's read-only mode; a
write fails, and the SQLite pragma is restored afterwards so a pooled connection is not left read-only.

## Related, not fixed

The same encoding affects **every field that goes through `strip_html`**, not just URLs: `Terms &
Conditions` is stored as `Terms &amp; Conditions`, a finding titled `IDOR on /orders?a=1&b=2` is stored
with `&amp;`, and the frontend has no entity decoder, so users see the literal `&amp;`. That is display
corruption rather than data a tool reads back; it is called out in the recovery plan and needs its own
decision.

## Tests

`tests/test_recon_url_integrity.py` (14): `&` survives every importer; nuclei keeps its matched URL; the
URL a runner will scan equals the URL that was discovered (through job preview); a literal `&amp;` is kept,
not decoded; `a&b` and `a&amp;b` are no longer collapsed; a URL is never stored as markup; titles are
still sanitised; control characters and length; and the boundary with legacy rows (left exactly as stored;
a re-import adds the correct row beside the old one; an httpx host heals itself). Pointing the helper back
at `strip_html` turns 11 of them red.

`tests/test_audit_recon_urls.py` (11): corroborated, unpaired, collisions, cross-engagement peers not
counting as evidence, the post-fix cutoff, nuclei, that it changes nothing and cannot write, that it
leaves the connection writable, and that an unknown database is refused rather than audited blind.

925 backend tests.
