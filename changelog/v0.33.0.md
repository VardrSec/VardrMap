# v0.33.0 — 2026-08-17

## Security: headers were missing from CORS preflight responses

`CORSMiddleware` answers a preflight itself and returns without calling the app
beneath it. `SecurityHeadersMiddleware` was registered *inside* CORS, so every
`OPTIONS` response went out with no `X-Frame-Options`, no CSP, no
`X-Content-Type-Options` — and the same short-circuit applied to anything else
CORS produced.

The chain is now `SecurityHeaders → CORS → LegacyProgramPath → SlowAPI → app`.
Being outermost also means the headers survive paths that never reach a route
handler: auth failures, rate-limit rejections, validation errors and unmatched
routes. `LegacyProgramPath` stays outside `SlowAPI` so rate limiting still keys
on the rewritten `/engagements/*` path.

**HSTS is production-only, and now says so.** The check was `ENV != "development"`,
which also matched `test`, `staging`, and any typo — a browser hitting a
non-HTTPS deployment could be pinned to HTTPS for two years. It is now an exact
`ENV == "production"` match, so an unrecognised environment fails to the safe
side.

**Unhandled exceptions were the one gap ordering could not close.** Starlette's
`ServerErrorMiddleware` wraps every user middleware, so an exception escaping the
app produced a bare `500` that no user middleware could stamp — verified before
the fix. Registering an `Exception` handler on the app does not help, because
that handler is invoked by the same outer middleware. `SecurityHeadersMiddleware`
now catches the exception itself and returns a sanitized
`{"detail": "Internal Server Error"}`, logged with a stack trace but never
exposing one.

`backend/tests/test_security_headers.py` covers all of it: normal responses,
401s, cross-user 404s, 422s, unmatched routes, unhandled 500s, CORS preflight
(including on the deprecated `/programs` path and from a disallowed origin), HSTS
present in production and absent in development, test, staging and a near-miss
typo.

## Reports are client deliverables, not bounty submissions

**Breaking: the report status values changed.**

| Old | New |
|---|---|
| `draft` | `draft` |
| — | `internal_review` |
| — | `final` |
| `submitted`, `accepted`, `resolved` | `delivered` |
| `duplicate`, `informative` | `archived` |

The old vocabulary described a bounty platform's verdict on a submission. The new
one tracks the document's journey to the client. `archived` is reachable from any
state, not only from `delivered` — a draft superseded before it reaches a client
still needs somewhere to go.

Retired values are now rejected with `422`. Migration `0022reportlifecycle` maps
stored rows; it is UPDATE-only, so no column, table or row is dropped. The
downgrade restores the old vocabulary and is lossy where the forward map
collapsed several values, which the migration docstring records.

**Transitions are not enforced, deliberately.** These are independent workflow
labels: a report can be created directly as `delivered`, moved back to `draft`
after client feedback, or `archived` from any point. The same reasoning applies
as to scope (ADR 0001 § Amendment) — the platform records what the operator says
is true rather than policing it, and a transition guard would block legitimate
work such as importing an already-delivered report. Pinned by tests so the
absence of enforcement is a guarantee rather than an oversight.

## Fixed API contract drift

- `serialize_report()` now returns `created_at`. It was documented, stored, and
  used to order the list endpoint, but never serialized — a client following the
  docs got `undefined`.
- The engagement object example documented retired finding statuses `accepted`
  and `rejected`; it now shows the real lifecycle.
- The frontend `Engagement` type was missing `stop_work_at`, `stop_work_reason`
  and `org_id`, all of which the backend already serializes.

`test_docs_contract.py` now catches **obsolete** documented values, not just
missing ones. The previous checks asserted each enum value appeared somewhere in
the file, which is why `accepted` and `rejected` survived — the words existed
elsewhere. Checks are now pinned to a single line and compare both directions.

## Engagement creation asks what kind of engagement it is

The quick-create form collected a name, platform and URL, then let the API's
compatibility default make everything a `bug_bounty` engagement with no client,
no window and no authorization prompt.

It now asks for type, status, client and testing window, with the fields
conditional on type:

- **pentest** and **internal** offer a client picker
- **pentest** and **red_team** surface the written-authorization requirement,
  before creation and again in the confirmation message
- **bug bounty** asks for neither, and sends neither

The API default is unchanged, so existing callers that omit `engagement_type`
still get `bug_bounty`.

## Engagement overview shows operational state

A new panel above the stat cards surfaces engagement type, status, client,
active authorization, testing window, stop-work state and the caller's role,
plus a "setup incomplete" list naming what is missing. Everything comes from the
existing engagement object and the existing
`GET /engagements/{id}/authorization/active` endpoint — no new model or field.

## Performance: the engagement list no longer amplifies queries

`GET /engagements` called `serialize_engagement` in a loop, and each call issued
six `COUNT`s plus two `GROUP BY`s and lazily loaded scope items and import
records — roughly ten queries per engagement.

`serialize_engagements()` folds each aggregate into one grouped query over the
whole page, and the endpoint eager-loads the two relationships. Query count is
now constant in the number of engagements. `serialize_engagement()` delegates to
the batch path, so the list and detail endpoints cannot drift apart in shape.

**Role resolution was a second, hidden N+1.** `engagement_access()` returns
`"owner"` before issuing any query, so a caller who owns every engagement never
pays for role lookups — and the first query-count test used exactly such a
caller, which is why it passed while an invited member, viewer or organization
member still paid two extra queries *per engagement*. `_resolve_roles()` now
batches the whole page into two queries, preserving the precedence
`owner > organization role > direct engagement membership`. Tests cover invited
members, viewers, organization-only members, mixed access paths, and parity with
`deps.engagement_access` on every precedence combination.

`test_engagement_list_queries.py` guards it with a ratio rather than an absolute
budget: serializing four engagements must not cost more queries than one.
