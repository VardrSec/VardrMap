# v0.29.0 — 2026-08-16

## Scope enforcement becomes advisory

**Breaking: job creation, job claim, and `PATCH /jobs/{id}` no longer return
`403` for scope, window, or authorization findings.** They return `200` with a
`warnings` array, and the job runs.

VardrMap still evaluates every job against the engagement's authorization,
testing window, and scope rules — that machinery is unchanged. What changed is
what it does with the answer: it tells the operator, and gets out of the way.

### Why

Enforcing scope means interrupting paid work whenever the platform's reading of
a rule disagrees with the operator's. Scope in the field is messier than any rule
set — verbal expansions mid-engagement, hosts that appear overnight, ranges that
shift — and v0.28.0 showed the failure mode concretely: tightening subdomain
matching silently started denying jobs on engagements that had been running fine.

Being wrong in that direction costs an engagement. Being wrong the other way
costs a warning someone chose to ignore.

The broader point is that this is a tool, and the tools it sits alongside do not
police their users. Burp proxies any host you point it at; nmap scans any range
you hand it. Responsibility for staying inside scope belongs to the operator.

### What you get instead

```json
{
  "id": "<uuid>",
  "status": "pending",
  "warnings": [
    { "reason": "target_out_of_scope",
      "message": "api.acme.com does not match any in-scope rule." }
  ]
}
```

Empty when nothing is flagged. The reason codes are unchanged and remain a public
contract — `engagement_not_active`, `authorization_missing`,
`authorization_not_active`, `outside_testing_window`, `capability_prohibited`,
`target_excluded`, `target_out_of_scope`, `scope_ambiguous`. A client that wants
to treat a warning as fatal can branch on them.

### Stop-work still refuses

`stop_work_active` is the exception and still returns `403` at all three points.
It isn't the platform second-guessing the operator — it's the operator's own
emergency brake, and a brake that can be ignored is not a brake.

Transitions to `done` / `failed` remain ungated, so a runner can always report
the outcome of work already performed.

### Warnings are not audited

Denials were previously written to `audit_logs` with `action="deny"`. That is
removed: a scope finding is advice to the operator, not a security event filed
against them. Stop-work engage/release is still audited. The `reason` and
`detail` columns stay on the table, now unused by this path — no migration.

### Migration note

No database change. Callers that branch on `403` from these three endpoints need
updating: the status is now `200` and the information is in `warnings`.
VardrRunner needs no change — it simply stops receiving `403` on claim.

### Tests

670 backend tests. `test_policy.py` is untouched — the decision logic didn't
change. `test_execution_policy.py` now proves the wiring: findings surface as
warnings at all three evaluation points, a warned job is still queued, warnings
are absent from `audit_logs`, and stop-work still refuses.
