# v0.41.0 — dalfox as a job type, with its verification signal intact

**Date:** 2026-10-09

`dalfox` becomes a queueable job type, a Composer tool and an import type. **Pairs with
VardrRunner v0.46.0**, which adds the handler. Migration `0026` (additive).

dalfox reports XSS **candidates**, and the whole design of this change turns on that word.

## Candidates, not findings

Everything dalfox imports lands as a scan item with `status: "new"`. Even its top tier means
*dalfox asserts* this input is exploitable — not that this platform confirmed it — so no
tier maps to a confirmed status and promoting a candidate stays an operator's act. The
Composer copy says "XSS candidates", and the webhook says "candidate(s)" rather than
"finding(s)", because calling an unverified match a finding in an alert is how a scanner
result quietly becomes a reported vulnerability.

## The scanner's own signal is preserved, not flattened

dalfox reports three independent facts about a match, and an operator triaging it needs all
three. "Reflected, by reflection, low confidence" is a very different thing to act on than
"vulnerable, by dom-verification, high confidence", even where severity agrees.

| Field | Values |
|---|---|
| `type` | dalfox's tier: `vulnerable` (`V`), `reflected` (`R`), `ast` (`A`), `informational` (`I`) |
| `detection_method` | `reflection`, `dom-verification`, `ast`, `oob`, `library` |
| `confidence` | `high`, `low` |

`detection_method` and `confidence` are new columns (migration `0026`, additive, defaulting
to `""`). Packing them into the existing free-text description would have made them
unqueryable, which defeats the point of keeping them. A value dalfox does not define is
dropped rather than invented into our vocabulary, and `severity` is carried through as dalfox
grades it — `R` stays `info` — with nothing here upgrading it.

Response bodies are never stored: `request`/`response` (present with `--include-all`) are
ignored.

## The payload and evidence are stored exactly as reported

An earlier revision ran everything through the generic sanitiser. That is the right defence for
prose and the wrong one here: it deletes anything shaped like a tag and HTML-encodes `&`, so the
payload `<svg onload=alert(1)>` was stored as **nothing** (and dalfox's message read `q=`), and a
PoC URL `?a=1&q=x` became `?a=1&amp;q=x`. For a tool whose whole output is "this input is
dangerous", that input is the evidence, and a tester was left unable to reproduce the issue. Found
by checking the stored row against a real dalfox report rather than against a fixture.

- `payload` and `match_evidence` are **new columns** (added to migration `0026`, which had not
  shipped, so no `0027`) holding the scanner's text exactly: control characters removed,
  2000-character cap, nothing else. Exposed on `GET /scans`.
- The PoC URL in `asset`/`matched_at` is kept exactly and dropped entirely if it is not `http(s)`.
- The parameter and injection context that form the dedup identity are no longer sanitised either:
  two parameters shaped like tags used to collapse into one key and one of them was lost.
- `description` is still sanitised and now says `q=[payload]` instead of quoting a payload the
  sanitiser would mangle.
- **Safe to store raw** because it is data, not markup: the API returns it as a JSON string and
  nothing in the frontend renders HTML. It is documented as untrusted text that must only ever be
  rendered as text; a future consumer that renders HTML must escape it.

Nineteen regression tests anchor on a verbatim real finding. Re-pointing the helpers at the old
sanitiser turns 13 of them red.

## dalfox imports are deduplicated

Unlike nuclei, a dalfox re-scan re-reports every match it still finds, which would inflate
the engagement's count on every run. The dedup key is the URL **without its query values**,
the injection context and parameter (stored together in `template_id`), and the tier.

It deliberately excludes the payload and the PoC URL. dalfox mints a fresh marker class per
payload (`class=dlx1ec4110f`) and that marker lands in both, so keying on either would make
every re-scan look like new findings — the exact failure the dedup exists to prevent.

A tier change is new information, not an update in place: a parameter that moves from
`reflected` to `vulnerable` is stored as its own row rather than silently merged.

## Fix: `/scans?job_id=` now matches recon and services

A deduplicated re-scan stores nothing, so its `job_result_links` rows are the only record
that it saw the issue at all. `GET /scans?job_id=` filtered on the creator stamp only, so
such a job appeared to have found nothing. It now returns the rows a job produced **plus**
the ones it observed, which is what `/recon` and `/services` already did — and what
`docs/architecture.md` already claimed for all three.

## Queueing it

```http
POST /engagements/{id}/jobs
{ "tool_type": "dalfox", "target_source": "recon",
  "config": { "limit": 100, "worker": 10, "delay": 100, "mining": true } }
```

`worker` (1–100) caps concurrency and `delay` (0–10000 ms) spaces requests out: dalfox sends
payloads at every parameter it finds, so its load is bounded at queue time like any active
tool. `mining` controls parameter discovery.

## Scheduling: dalfox can recur

Schedules and scan profiles validate `tool_type` against the same set as jobs, so allowing
`dalfox` as a job type also makes it schedulable. Nothing in code changes for that; it is
recorded because a recurring active scanner deserves saying out loud (detail in
`docs/api.md` § Scheduling active tools).

- **Repeated schedules mean repeated active traffic**, from `hourly` upward. `worker` and
  `delay` limit **one execution, not the engagement**: nothing aggregates traffic across runs,
  schedules, or overlapping jobs.
- **Execution limits are preserved**: validated when the *schedule* is created, so a schedule
  cannot remove the concurrency cap, and carried unchanged by every job it materializes.
- **Policy is evaluated at claim, not at schedule creation**: authorization, window and scope
  findings come back as `warnings` and the job still runs (ADR 0001), so a schedule keeps
  running after the authorization window closes, each run carrying the warning. Stop-work
  refuses the claim with `403`.
- **Stop-work does not pause a schedule**: due schedules keep queueing a pending job per
  interval, claimable on release. Pre-existing for every tool and unchanged here; disable
  active-tool schedules when engaging a long stop.
- A recurring scan stays deduplicated, and a later run still records that it observed a known
  candidate, so it does not look as though it found nothing.

Ten new tests cover the scheduled path: creation, rejection of six limit-evading configs, the
config surviving materialization, warnings at claim, and the `403`.

## Tests

`backend/tests/test_dalfox.py` (32): the job type and every out-of-range or unknown config
key; that tier, detection method and confidence survive import and that each tier maps to its
own name; that even `V` lands as `new`; that `R` keeps its lower severity; that an undefined
signal value is dropped; that `--include-all` response bodies are not stored. Then dedup — a
re-import adds nothing, a fresh payload marker is still the same finding, duplicates within
one upload collapse, and a changed parameter, context, tier or URL is its own row — and
provenance: a new candidate links to its job, a later job that re-observes a known candidate
still records that it saw it, and a made-up `job_id` is refused with nothing stored.

881 backend tests, 136 frontend; lint, typecheck and build pass. The migration was verified
to apply, preserve existing rows and reverse.
