# v0.26.0 — 2026-08-12

## The asset graph — the attack surface gets a spine

A host used to exist as **five unrelated free-text columns** with no foreign key
between them:

| Table | Column | Type |
|---|---|---|
| `recon_items` | `host`, `url` | `Text` |
| `services` | `host` | `String(500)` |
| `scan_items` | `asset` | `Text` |
| `findings` | `asset` | `String(500)` |

Identity resolution was string comparison — "url when present, else host" — so
`api.acme.com`, `https://api.acme.com/` and `api.acme.com:443` were three
different things. A finding could not be traced to the service that exposed it,
risk could not be aggregated per host, and attack surface could not be diffed
over time. "Everything we know about this host" was a fuzzy `LIKE` across four
tables.

### What exists now

`assets` is the node table, keyed by `canonical_key` — a pure function of the
observed string, **unique per engagement**. `asset_relationships` is a directed
edge table with `resolves_to`, `hosted_on`, `exposes`, `discovered_from`,
`belongs_to`, and `vulnerable_to`. All four observation tables gain a nullable
`asset_id`.

Nodes carry provenance: `source`, `confidence`, `first_seen_at`, `last_seen_at`,
plus operator-set `environment`, `criticality`, `exposure` and `tags`.

### Correlation happens at the host

Observations link to the **host-level** node; port-specific nodes exist for
services and link back with an `exposes` edge.

This was not the first design. The initial version linked a recon row recorded
as `https://api.acme.com/v1` to `domain:api.acme.com:443` and a finding recorded
as `api.acme.com` to `domain:api.acme.com` — two nodes that never join, leaving
the graph exactly as fragmented as the columns it replaced. The migration test
caught it. There is now a named regression test for it.

### Unclassifiable input stays unlinked

`parse()` returns `None` rather than forcing a value into a bucket, and callers
treat that as "no asset link", never an error — a malformed host in one row of a
tool export must not fail the whole import. **A NULL link is recoverable; a
wrong merge is not**, because after a merge there is no record of what was
distinct.

Credentials in a URL are stripped before identity is computed, so a userinfo
segment can never become part of an asset key.

### Live ingestion

`httpx`, `ffuf` and `nuclei` imports resolve and link their rows. Service
uploads create both the host node and the port-specific service node, and the
`exposes` edge between them.

### Read API

- `GET /engagements/{id}/assets` — list, filter by `asset_type`, prefix-search
  by hostname (deliberately not a leading-wildcard `LIKE`, which would scan)
- `GET /engagements/{id}/assets/{asset_id}` — one asset with its edges and
  joined counts for recon, scans, services and findings. **This is the query the
  graph exists for.**

### Migration `0018_asset_graph`

Creates both tables, adds the four columns, then backfills every existing
observation through the same normalizer the application uses. Verified on a
seeded database: a URL row, an uppercase-hostname row, and a finding all
converged onto **one** asset; an unparseable row was left unlinked; `downgrade()`
dropped both tables with every observation row intact.

Backend suite: 568 → 599.
