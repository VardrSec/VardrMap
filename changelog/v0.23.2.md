# v0.23.2 — 2026-08-09

## Wait for Postgres before migrating, so deploys stop crash-looping

Railway deploys were failing with:

```
Running Alembic migrations...
psycopg.OperationalError: connection failed: ...
FATAL:  the database system is starting up
```

Nothing was wrong with the migration. Railway starts the application container
and the Postgres service **concurrently**, and a database still in recovery
*accepts* the TCP connection and then answers `FATAL: the database system is
starting up` — it does not simply refuse it. `alembic upgrade head` exits
non-zero, `set -e` in `start.sh` kills the container, and Railway restarts it.

`railway.json` sets `restartPolicyMaxRetries: 3`. Three restarts happen within
seconds of each other, all landing inside the same recovery window, so the
budget is exhausted long before the database is ready and the deploy fails
permanently — waiting out a condition that clears on its own in under a minute.

Free-tier services make this reliable rather than occasional: they cold-start on
every deploy, so the app and the database race from a stop every single time.

### The gate

`backend/wait_for_db.py` polls `SELECT 1` every 2 seconds for up to 120 seconds
before `start.sh` runs alembic. It reuses the engine from `db.py` rather than
building its own connection, so the check exercises the exact connection path
the application uses — psycopg3 scheme rewrite and `sslmode=require` included —
instead of an approximation that could pass while the real one fails.

A database that never comes back still fails the deploy: after the timeout the
last connection error is re-raised and the process exits non-zero. The gate
converts a transient failure into a wait, not every failure into a hang.

### Tests

Four, covering the paths that matter: immediate success, failure-then-recovery
(the actual production scenario), and timeout on a permanently unreachable
database. The fourth asserts `start.sh` runs the gate *before* `alembic upgrade
head` — ordering is the entire point, and a gate that runs after the migration
does nothing.

Backend suite: 464 → 468.
