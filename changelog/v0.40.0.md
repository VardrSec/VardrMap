# v0.40.0 — ffuf as a job type

**Date:** 2026-10-09

`ffuf` becomes a queueable job type and a Composer tool. **Pairs with VardrRunner
v0.43.0**, which adds the handler that executes it.

ffuf output was already importable — `parse_ffuf` predates this release, and the manual
import dropdowns have always listed it. What was missing is the ability to *queue* it, so
content discovery had to be run by hand and uploaded. Now it queues like every other tool,
including as a pipeline stage.

## Queueing it

```http
POST /engagements/{id}/jobs
{ "tool_type": "ffuf", "target_source": "recon",
  "config": { "wordlist": "common", "extensions": ".php,.bak", "rate": 25 } }
```

| Config key | |
|---|---|
| `wordlist` | A **name** matching `[a-z0-9][a-z0-9_-]{0,39}`, e.g. `common`. Never a path. |
| `extensions` | `.php,.bak` — comma string or list; a bare `php` gains its dot. |
| `match_codes` | Three-digit statuses (`200,301,403`), or `all`. |
| `rate` | Requests per second, per target. 1–1000. |
| `limit` | Max recon items to use. 1–1000000. |
| `timeout` | 1–86400 s. |

Every key is optional; VardrRunner supplies its own defaults for the ones left out.

The accepted **types** mirror VardrRunner's `FfufConfig` exactly: `match_codes` takes a bare
status code (`200`) as well as a string or list, because that is what a JSON caller naturally
sends; `extensions` takes only strings and lists, since an extension is never a number.
`bool` is refused by both — `True` is an `int` in Python, and a status of `1` is nobody's
intent. Keeping the two in step matters because a type this API accepts and the runner
refuses produces a job that clears queue-time validation and then fails on the operator's
machine, which is the failure mode validating here is meant to prevent. Both repos carry the
same table (`test_accepted_types_match_the_runners` /
`test_accepted_types_match_vardrmaps_validator`) so the pair cannot drift.

## The wordlist is a name, not a path

`config.wordlist` must be a bare name. VardrRunner resolves it against
`~/.vardrmap/wordlists` on the machine running the scan. A path, a traversal, or a drive
letter returns `400`.

This is the point of the field's design. If a job could carry a path, this API would be
able to name any file the runner's user can read, and ffuf would read that file and replay
its lines as paths at a target — a file-disclosure primitive assembled from two features
that are each individually reasonable. The pattern here mirrors VardrRunner's
`configs.WORDLIST_NAME` exactly, and the runner refuses a path independently, so accepting
one here would only queue a job that could never run.

## The rate cap is a safety control

`config.rate` bounds the load one job can put on a client's host — ffuf is the only tool
in the catalog that generates sustained traffic, and ffuf's own default is unbounded
threads. So the key has a ceiling of 1000 and **no value meaning "unlimited"**; `0` and
negatives are refused. Omitting it gives the runner's default of 50/s.

VardrRunner additionally always runs ffuf with auto-calibration, so a host that answers
every path with `200` cannot flood an engagement's shared recon store with thousands of
phantom endpoints. Wrong data in an engagement's record is worse than no data.

Scope remains advisory, as everywhere else (ADR 0001): an ffuf job outside scope comes back
with `warnings` and still runs.

## Known rough edge: preview counts recon rows, not roots

`config.limit` caps **recon rows**, and VardrRunner collapses ffuf's targets to site roots
*after* that cap. So 100 recon URLs on one host consume the default limit and fuzz one root.
`POST /jobs/preview` has the same shape — it resolves recon targets, not roots — so for
`ffuf` its `count` is an upper bound on the hosts touched rather than the exact execution
set. Documented in `docs/api.md`. Collapsing roots in preview would mean a second copy of
the runner's normalization in the backend, and a divergent second copy is what produced the
type mismatch this release also fixes, so it is left for a shared fix.

## UI

The Composer gains an ffuf entry — `wordlist`, `extensions`, `match_codes` and `rate`,
against recon or scope. Its wordlist placeholder is a name (`common`), not a path, so the
field does not walk an operator into a `400`.

**Pipelines are unchanged.** ffuf is active and noisy, so it is not added to Content
Discovery or any other named chain; it is queued deliberately, ideally against hosts httpx
has already confirmed live. It is accepted as a stage in any pipeline posted to the API.

## Tests

`backend/tests/test_ffuf.py`: the job type is accepted with a full config, an empty one and
in a pipeline stage; eleven path-shaped or malformed wordlists are refused (absolute paths,
traversals, both drive-letter spellings, an extension, uppercase, whitespace, over-length,
an option marker, a non-string); bad extensions, statuses, rates, limits and timeouts are
refused at queue time; the rate cap cannot be disabled; unknown keys are refused. Plus the
import path both ways — a raw ffuf report and the runner's JSONL produce identical recon,
and duplicates within one upload are dropped.

`toolCatalog.test.ts` asserts ffuf's sources, its config keys and that its wordlist
placeholder contains no path separator.

871 backend tests, 136 frontend.

## No migration

Job types are validated in code against a set, not stored in an enum, so nothing changes in
the database.
