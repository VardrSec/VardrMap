# v0.21.0 — Scan automation & integration

**Date:** 2026-07-22

Five changes that tie the scan input → output → triage loop together, so tools
and their results are integrated rather than isolated islands.

## Added

- **Scan pipelines** — `POST /programs/{id}/pipelines` queues an ordered chain of
  jobs where each stage waits on the previous one. The canonical recon pipeline
  subfinder → httpx → nuclei is now one request / one click. `scan_jobs.depends_on`
  links stages; a dependent stage is withheld from `GET /jobs/pending` until its
  parent is `done`, and auto-failed (never hung) if the parent failed. Per-stage
  validation is identical to single-job creation, so a bad stage rejects the whole
  pipeline atomically.

- **Job → results provenance** — `recon_items.job_id` and `scan_items.job_id` now
  record which scan job produced each row. The import endpoint accepts an optional
  `job_id` form field (VardrRunner passes the id of the job it is executing), and
  `GET .../recon?job_id=` / `GET .../scans?job_id=` filter by it — so the Terminal
  can deep-link from a finished job straight to exactly the rows it yielded.

- **AI triage over raw scan output** — `POST /programs/{id}/scans/triage` sends a
  batch of un-promoted `scan_items` to Claude and returns a per-item
  `priority` / `false_positive` / `rationale`, turning the nuclei firehose into a
  ranked queue. Distinct from `findings/{id}/suggest`, which only enriches a finding
  you already created. Only ids present in the request are echoed back. Requires
  `ANTHROPIC_API_KEY` (already used by the suggest endpoint — no new env var).

- **Dry-run target preview** — `POST /programs/{id}/jobs/preview` resolves the target
  list a job would run against (count + a 20-item sample) without queuing anything,
  so the Composer can confirm intent before launching a large scan.

- **Saved scan profiles** — `GET/POST/DELETE /programs/{id}/scan-profiles` store
  reusable tool + config presets per program (e.g. "nuclei CVE sweep"), validated
  identically to job creation. Queue a frequently-used scan in one click instead of
  retyping config.

## Security — viewer role is now truly read-only

`require_member_write` was applied inconsistently: only findings (add/delete),
reports (add/delete), and scope endpoints enforced it. A `viewer`-role member could
still queue jobs, import files, change scan/finding/manual-test status, create
submissions and schedules, and trigger paid AI calls. This release adds the guard to
**every** program-scoped write endpoint (findings update/suggest, reports update,
manual tests, scans status + triage, jobs, pipelines, scan profiles, submissions,
schedules, services, imports). Owners and runner-scoped keys (which resolve to the
owner) are unaffected; only viewers are blocked, with `403`.

## Schema

Migration `0013pipelineprofiles` (additive):
- `scan_jobs.depends_on` (nullable)
- `scan_items.job_id` (nullable)
- new `scan_profiles` table

## Frontend

- **Composer** (`jobs/Composer.tsx`): a "Recon Pipeline" one-click button (POST
  /pipelines), a "Preview" button showing resolved target count + sample before
  queuing, and a saved-profiles row (load a preset into the form, save the current
  config, delete). `JobsSection` supplies the handlers and loads profiles on mount.
- **Scanning** (`ScanningSection.tsx`): a "Triage with AI" button that ranks the
  loaded scan results (priority chip + false-positive flag + one-line AI rationale
  per row).
- **Provenance link**: the Terminal's "→ View results" button (done jobs) now
  carries the job id through `NAVIGATE_TO_REVIEW`; `ReviewSection` forwards it to
  Recon/Scanning as a `job_id` filter with a "showing results from one job — clear"
  banner.
